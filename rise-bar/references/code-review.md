# Code review, lint, and regressions

## Diagnose before modifying

Count warnings in the current checkout without reusing totals from an earlier session. Use the same `qmllint` version, imports, and options before and after. Record files analyzed, warnings, categories, and failures; a zero exit status does not mean there are no warnings.

The project runner counts console lines beginning with `Warning:`. The JSON report may also include diagnostics that the console does not show. Use JSON to locate suggestions, but do not mix the two metrics when reporting a reduction. Do not reduce coverage or disable categories to obtain a lower count.

### `PanelWindow` and metadata

Tooling may resolve the public `PanelWindow` type as the non-instantiable `Quickshell._Window` interface, while the runtime selects a platform implementation. This can produce `Type PanelWindow is not creatable. [uncreatable-type]` for valid code. The Quickshell documentation describes language server limitations when resolving `PanelWindow`:

https://quickshell.org/docs/v0.3.2/guide/install-setup/

Do not assume every warning in this category is false. Check imports, the installed version's `.qmltypes`, and a minimal example. Confirm on Wayland with an isolated hidden window, without loading the production bar. If the example loads, relevant tests pass, and logs are healthy, report the tooling limitation and preserve the component. Do not modify metadata in `/usr/lib`, switch backends, or add suppressions merely to clear lint. Do not hardcode a warning count in the skill: it varies with code and dependencies.

For a broad review, record which components produce warnings and compile those components in the runtime. Compiling with `Qt.createComponent` does not instantiate panel services; this and a hidden window validate resolution/loading, but do not prove interaction with every panel.

## Fix scope without changing behavior

- Qualify external object references with the correct ID, such as `notifPanel.root`. Distinguish the external `root` ID from an internal component's `root` property; a collision may point to the wrong object.
- Use `pragma ComponentBehavior: Bound` when internal components need IDs from their creation context. Check delegates afterward: roles previously injected implicitly by the model may need `required property var modelData` or `required property int index`.
- Use clear local IDs for properties in inline components and delegates. Do not globally replace identifiers without checking scope, comments, strings, and handlers.
- Automatic lint suggestions help insert prefixes, but review the diff. JSON offsets use UTF-16 code units; do not apply them as UTF-8 byte indices. Inserting an ID into a single-line declaration also requires a valid separator.
- Preserve commands, arguments, visibility guards, and timers. Capture data before updating models that may destroy the delegate.

## Shared contracts, responses, and resources

When extracting or fixing a shared panel, check the V1 and V2 root contracts. A property present only in V2, such as `aiUsageReveal`, must not be implicitly required in V1. Test opening/closing with both roots and preserve animation progress where it exists.

### Optional facade hooks must not block panel lifecycle

1. Trace the complete handler chain before changing a popup: widget identity, panel open/close, controller show/hide, focus and the next action. If authentication or another launcher runs after `close()`, test that boundary too; an exception during dismissal can prevent the unrelated action from starting.
2. Verify optional API behavior, not only member existence. A method exposed through a QML facade may exist and still throw when its callback writes a read-only property. Cover both a missing method and a present method that throws the observed exception; a successful mock mutator conceals this failure.
3. When an optional cosmetic hook is explicitly removed, remove its callers and local helper together while retaining the standard controller lifecycle. Do not replace a failed method call with assignment to the same read-only property, modify the global shell API, or remove unrelated Google/API functionality.
4. Make the regression fail before the patch and verify that opening, closing and reopening no longer call the broken hook. Treat extracted JavaScript/controller-stub tests as narrow behavior evidence only; actual QML pointer, focus and outside-dismissal still require a runtime check.
5. Compare installed files and fresh reload logs separately from source tests. Report an unavailable IPC target or absent graphical check as an acceptance limit, not proof that the new panel closed successfully.

The Wallpaper Manager controls live in `shared/panels/WallpaperManagerQuickPanel.qml`; the V1/V2 adapters retain geometry, radii, surface decoration, and V2 reveal animation. Change shared controls there rather than restoring duplicate interfaces. Keep adapter references to the card through `panel.surfaceHost`; the shared card's private ID is not in the adapter's scope.

When a `surfaceComponent` Loader reparents decoration to `surfaceHost`, the new child can be appended above existing content. Give background surfaces an explicit stacking order behind the controls (`z: -1` for the Wallpaper Manager's V2 `ConnectedPanelSurface`), and preserve the intended ordering of accent rails and shadows. A surface covering content may make labels look almost invisible and intercept clicks even though bindings and control tests pass.

### Widget adapters and media presentation

Keep state, timers, commands, and interaction in the shared widget; let adapters supply colors, label visibility, spacing, compact/full mode, and decoration. Similarity alone does not justify merging `Theme.qml` or `VariantRoot.qml`: inspect their preferences and composition contracts separately. Consult the checkout's shared-components inventory for the current extraction map.

Preserve typed QML color intermediates before reading `.r`, `.g`, `.b`, or `.a`. A theme helper or mock may return a CSS string; replacing `property color contentColor: helper(...)` with `helper(...).r` removes the conversion and can silently change transparency. Check inactive, active, filled, and disconnected colors where relevant.

Replacing Row with Grid can change implicit size even when the visible pixels initially match. V1 Tray sizes only visible cells; V2 intentionally reserves model columns. Preserve `reserveHiddenColumns` and test empty, partially pinned, fully pinned, and vertical states. Compact widths may also need explicit state bindings because a Row's implicit size updates during layout rather than synchronously with a setting change.

The shared MPRIS panel accepts variant-specific capture commands, attack/release, cover source, and palette. V1 retains its pulse capture and single accent; V2 keeps pipewire capture, artwork resolution, and `variants/V2/modules/MprisPanelPalette.qml`. Preserve these differences and the connected surface's negative stacking order instead of introducing V2-only root requirements into V1.

Validate the entire response being used before replacing the displayed state. Catching an exception after updating temperature, location, or other fields can leave new data alongside an old forecast. Cover valid JSON with an invalid structure, incomplete lists, null entries, and zero values; do not use truthiness as numeric validation.

Packaged resources should resolve relative to the module, for example `Qt.resolvedUrl("../quotes.txt")`, instead of using old installation paths under `~/.config/quickshell`. Preserve the same configuration root and relative structure in the fixture: a resource outside the root may become `qrc:/qs-blackhole` in the Quickshell scanner. When a fixture needs real `FileView` behavior or plugins linked to the Quickshell executable, use `qs`; `qmltestrunner` alone may not load those plugins.

For scanner limits, check the work before materializing the collection. Limiting processing after `list(os.scandir(...))` does not limit enumeration or memory use. The regression should count consumed entries as well as returned results.

## Choose tests that actually exercise the change

### Immutable candidates for parallel implementation and review

1. Assign the shared checkout and Git state to one implementation owner. Have the reviewer prepare acceptance criteria and test patches in private scratch. Do not run acceptance against a checkout still receiving new tracked or untracked files: wildcard discovery can ingest unfinished tests even if tracked hashes and HEAD stay unchanged.
2. Freeze a full commit and tree, then generate a `git archive` from that exact commit rather than copying the working directory. Supply archive checksum and a complete manifest of unique paths, sizes, file hashes and executable modes. Reject escaping archive paths and unexpected link members before extraction.
3. Verify archive path-set equality against the manifest and `git ls-tree -r --full-tree <commit>`; compare every member's content identity and executable bits, not a sample. Extract into the reviewer's private scratch and make the source read-only during tests. If inventory-based runners require a private Git index, state explicitly that this index is not the original commit identity.
4. Identify supplementary reviewer fixtures and patches separately from the product snapshot. Record their hashes and which run used them; a failed extra keyboard test remains a finding against the unchanged product, not proof that the delivered fixture already covered it.
5. Run focused gates, then the required broad gate only when its backend prerequisites are met. Verify the full snapshot inventory again afterward. If a shared-tree run was contaminated, retain and invalidate that result, then rerun against the exact snapshot; do not attribute the contaminated failure to the commit.
6. Carry a finding forward only while the affected content hashes still match. When a new candidate is supplied, validate that exact candidate instead of repeatedly clarifying or quoting a failure from its predecessor. Close findings at the tested evidence level: shared-component success does not close native adapter or live-session acceptance.

### Portable CI contracts and negative workflow tests

1. Inspect the requested event/branch matrix and existing release triggers before adding CI. Keep portable syntax/model checks separate from Quickshell, Wayland and host-pinned runtime gates; do not copy a native broad runner unchanged into a hosted portable job or call excluded gates passed.
2. Declare runtime/parser dependencies, least-privilege permissions and checkout `persist-credentials: false` explicitly. Assert required PR/push coverage semantically while preserving version metadata and unrelated release workflows.
3. Parse workflow YAML with a loader that preserves GitHub Actions' `on` key and validate expected mappings/types. Inspect root and job permissions, event names, runner selection, checkout configuration and shell steps; do not enforce security with unscoped substring assertions.
4. Add valid-YAML negative fixtures for a write permission followed by a misleading read comment, a privileged PR event followed by a misleading ordinary-PR comment, and an extra shell step interpolating an untrusted PR title while leaving the legitimate runner step intact. Require each checker invocation to reject the mutation. Never execute the mutant workflow or its shell payload.
5. Record local tool versions and exact command exits independently of declared hosted versions. A locally passing workflow checker and portable suite do not prove hosted Actions execution, dependency installation or native acceptance.

### Overlay keyboard and reactive fixture acceptance

1. Trace the actual focused item's ancestors in each overlay/tab. A handler on a sibling main card cannot receive bubbled keys from the tools overlay, and a handler conditional on one tab leaves the other tab's header unprotected.
2. Keep a common-ancestor Escape fallback for all overlay controls while allowing the focused editor to consume its own clear-first behavior. Exercise direct opening and pointer tab switching, then use real Tab/Backtab to focus header controls and press Escape. Assert one dismissal and focus returned to the actual Search or Health opener, including after reopen.
3. Run those cases against both variant adapters where integration is claimed. Merely changing a shared component's variantName or matching adapter source strings is not composed-adapter execution. Connect read-only/no-side-effect assertions to real inert command/service boundaries rather than an unused zero counter.
4. Build fake roots with notifying QML properties for every field mutated after construction. Assert a post-creation visibility change reaches a bound observer before relying on the harness. A plain JavaScript object's changed field can read correctly from JavaScript while existing QML bindings remain stale.
5. Preflight backend availability and permission before launching native probes or the broad suite. Keep an isolated-display requirement strict by default; do not silently substitute ambient sockets or relabel offscreen tests as layer-shell acceptance. If the user explicitly authorizes inert tests on the current session, carry that changed authorization to both implementer and reviewer and use a separately named opt-in path. Preserve blocked results from the earlier scope without treating them as permanent limitations.

### Native composition: complete fixtures and trustworthy verdicts

1. Inspect the panel, both adapters and their transitive surface/positioner dependencies before generating a fake root. Collect required properties, methods, return types and signals across that graph; a regex limited to direct panel.root references misses APIs consumed by child decorations. Supply inert geometry methods such as verticalAnchorY and setPanelInsetX where the production helpers require them, with notifying QML properties and correct color/boolean types. Keep process, persistence and service actions intercepted.
2. Run the smallest composed fixture and capture stdout, stderr and the Quickshell native log identified by that run. Read native/binary logs through Quickshell's supported log reader rather than decoding every `.log` file as UTF-8. Require expected assertions/markers, successful exit and no runtime ReferenceError, TypeError, binding-loop, invalid-Connections or assignment diagnostics in **either** channel. Include both `Unable to assign` and `Invalid assignment` forms; a PASS marker after another scene object's exception is a false green. Calibrate the guard with a real injected runtime error whose child still exits zero and emits all success markers, plus synthetic log-only cases. Require rejection without executing malicious payloads. Fix missing fake members/types in the fixture, not production behavior or blanket log suppression.
3. Keep backend admission explicit. For a private gate, verify the private runtime/socket and retain its default refusal of ambient-session fallback. When current-session testing is separately authorized, add an explicit option such as --allow-active-session or use a clearly labeled diagnostic copy; record that admission-only adaptation separately from the immutable product snapshot. Never rename or symlink a live socket merely to claim private isolation.
4. Discover the authorized socket, verify its type and owner, and keep HOME/config/cache/state in private scratch. Use Qt's software rendering and an empty platform theme where appropriate. Instantiate only the inert test panels, not the real bar; prohibit real VPN, account, monitor, recorder or settings actions. Bound execution and clean up only processes/windows created by the probe. Session-test permission is not permission to install, reload or publish the plugin.
5. Recheck the product snapshot hashes after testing and identify backend, fixture adaptations, remaining diagnostics and exact coverage in the report. Native import/loading, programmatic close-signal routing, real keyboard delivery and physical-device behavior are separate acceptance claims; do not promote one into the others.
6. Once a scratch-only fixture correction establishes the working boundary, integrate the complete inert root and error-rejection guard into the maintained test driver before declaring the mandatory gate repeatable. Preserve an explicit authorized-session opt-in and strict default admission. Freeze the successor candidate and run its unmodified driver; a supplemental patched runner is useful diagnostic evidence, not proof that the committed gate is trustworthy.

### QML disclosure, reflow and missed pointer events

1. Reduce the failure to one disclosure and the next real click. Run the smallest existing QtTest case; record the expected persisted effect, not merely that a control is visible.
2. Inspect geometry immediately after opening and again after render: the positioner's x/y, implicit size, childrenRect, viewport contentY, mapped control centers, visible/enabled state and stacking/hit target. Pending polish can leave a newly visible options row at the old origin even when its height is already nonzero.
3. Place an explicit QtTest `waitForRendering` readiness barrier after the state change and before mapping/sending the next click. Where geometry has a defined target, use a bounded condition as well. Keep these barriers identical with captures enabled or disabled: a `grabToImage` callback yields to the event loop, while an optional capture helper may return immediately when no output directory was requested.
4. Retain `mouseClick` on the actual control and assert its observable effect. Do not replace the event with `clicked()`, a controller call or direct preference assignment. When controls move into a disclosure, update old tests to open that disclosure and establish readiness before exercising them; retain their persistence and confirmation assertions.
5. If the click still fails after layout settles, inspect the actual hit target, hover-driven visibility, enabled state, clipping ancestors and parent/canvas bounds before changing coordinates again. Mapped coordinates inside the window are not proof that a partially overhanging badge can receive the event. Preserve Flow when wrapping is required unless evidence establishes a layout defect; changing to Rows/Column without a settled hit-test only disguises the race. Keep the failure open until the real pointer event produces its service/persistence effect; do not present an unsuccessful coordinate workaround as a fix. Remove temporary instrumentation after keeping a focused regression, then run component and V1/V2 adapter suites before broad validation or deployment.

### Visual alignment acceptance

1. Reproduce the user's screenshot with the production shared widget and the actual variant adapter, surface, fonts and orientation. Include inactive, one-active and multiple-active states, transitions, hover reveal and module-disabled state.
2. Measure the outer capsule, the visible icon group, its cells and the rendered glyph bounds separately. Inspect hidden-item space, positioner rows/columns, padding, text alignment and glyph bearings before selecting a fix; do not assume any one of them is the cause without a failing reproduction.
3. Assert both centered geometry and the visible result after layout/polish settles. `anchors.centerIn`, a centered placeholder or an opaque Item substituted for the real surface can all pass while the active glyph remains visibly offset.
4. Keep before/after renders under identical deterministic state. Do not activate real DND, idle, recorder or account services merely to obtain an active icon; inject inert coordinator state instead.
5. Preserve hover, click targets and the idle marker while correcting the active group. Avoid unexplained per-glyph pixel nudges that conceal the underlying layout contract. If rendered verification is unavailable, state that limit and do not mark visual acceptance complete.

Use existing fixtures and extend them for the affected V1/V2 variants and styles. For bindings and interaction, prefer loading production content over duplicating the implementation in the test. Validate observable effects: selected value, submitted identity, confirmation, count, worker shutdown, and late results after closing.

An offscreen fixture may replace the window with an Item/Rectangle and remove layer-shell properties. This tests the content, not the backend. When needed, supplement it with hidden Wayland loading. Do not start the real bar as a probe.

For surface extraction or reparenting, inspect the rendered panel with its real decoration. A fixture that replaces `ConnectedPanelSurface` with an empty Item cannot verify contrast, occlusion, or pointer interception; compilation and a passing control test do not establish visual equivalence. Preserve a focused stacking regression and verify the actual open panel when session access allows it; otherwise report that visual check as unverified.

For broad presentation extractions, compare reference and new renders using the same fonts, deterministic data, dimensions, theme, and backend. Include affected orientations, filled styles, and compact/full states. Wait for geometry and animations to settle before capturing: a partially animated progress bar can produce a false pixel difference. In V1 vertical fixtures, reproduce `standardizeSurface()` on the reference widget; comparing its standalone pill against the rail-adapted result is not an equivalent scene. Treat offscreen image equality as presentation evidence for those fixtures, not proof of every live Wayland interaction.

When updating flat-copy fixtures, materialize the real adapter's style bindings and component slots along with the shared body. Rebase resource/helper imports to the fixture tree, retain typed properties, and mock newly extracted helpers too. If a shell assertion reads through `qml-fixture-source.py`, inspect that materialized output before changing its expected binding; raw adapter text may differ from what the assertion receives.

Explicitly mock Process, FileView, collectors, and service boundaries before instantiating panels that query accounts or real state. Being hidden does not prevent `Component.onCompleted` from starting a query. Before changing a production helper signature or signal binding, search its consumers and hand-written mocks; preserve the methods, properties and signals the real implementation uses, including process completion, collector completion, watched-file changes and tray drop-area registration where applicable. Diagnose a missing mock member before altering production behavior, then complete the mock rather than suppressing the diagnostic or weakening the assertion.

Include secondary effects in isolation. Mocking pacman/sudo without mocking `notify-send` can still send real notifications through the inherited bus. Capture these calls in a fixture and verify the expected effect without accessing the session.

### Shared scanner and resource lifecycle

1. Inspect the actual native ownership API before naming a fix a lease. If it exposes only a writable boolean, distinguish external baseline state from temporary demand by cooperating adapters; do not claim control over arbitrary unrelated writers.
2. Instantiate two actual production adapters with one inert notifying device. Drive panel visibility, device-list changes and destruction through QML events, not direct release-helper calls. Reproduce A-open/B-open/A-close, both complete close orders, destruction with a surviving owner, both owners switching devices, initially enabled state and duplicate refresh/release. Assert both continuing demand and final cleanup; a single-adapter green test misses order-dependent disablement and stale-true resurrection.
3. When shared coordination is required by a reproduced interleaving, key participating ownership by the exact resource-object identity. Capture its initial state once at first acquisition, deduplicate owners, and restore the initial state only after the last participating owner releases. Release the previous resource on replacement and the current resource on destruction; make repeated acquisition/release idempotent and remove empty registry records.
4. Run the same negative lifecycle cases before and after the change, retaining reverse-order and initially-enabled controls. Check model notifications, resource replacement and destruction rather than only registry counters; correct counters do not prove the native boolean is restored at the right time. Wait until QML deferred `destroy()` has actually completed before resetting shared fake-device baseline state or starting the next case; otherwise a previous owner's delayed destructor can mutate the next case and produce a false product failure. Retain the original log and repair only the readiness barrier, not the expected ownership assertions.
5. Keep native services and notifications inert. Report cooperative ownership, actual functional cases and remaining external-writer limitations separately from performance or physical-device claims. A passing helper/callback freshness test likewise does not establish QML timer scheduling or real suspend/resume expiry.

Permission fixtures must control the simulated chain of trust. `/tmp` is writable by other users; actual configuration directories may also have different permissions than expected. Mock metadata for ancestors outside the fixture while retaining real checks inside it, including rejection of directories writable by third parties. Do not change user permissions or weaken production validation to make a test pass.

For headless tests, use a temporary runtime directory with mode 0700, `QT_QPA_PLATFORM=offscreen`, the software backend, and `QT_QPA_PLATFORMTHEME=''`. Failure to create an IPC socket under a sandbox may be an environmental restriction: confirm in the authorized context before modifying code. Do not ignore `ERROR` or declare success while a test is blocked.

When a test extracts QML JavaScript for Node, isolate the complete intended function rather than slicing to the name of a later sibling method; intervening declarations can make valid production code fail to parse as one expression. Use the existing brace-aware extractor where appropriate, provide inert stubs for called siblings and cross-check a real QML fixture when extraction is uncertain. Align guard arguments and mock signal contracts with the production controller, while keeping accelerated fixture timing separate from the public timeout contract.

Regressions that compare exact text may need adjustment after qualifying references. Preserve the assertion's intent and retain behavioral validation; do not weaken a test to make it pass. For safety controls, distinguish an unknown state from a confirmed mismatch: preserve no-mutation assertions and test the message belonging to each actual state instead of changing production guidance to satisfy an unrelated wording check. Also consider runtime diagnostics: QtTest may pass with `ReferenceError`, `TypeError`, `Binding loop`, or `Unable to assign` in the log.

### Compare an external shell or plugin suite

1. Identify the exact local sources and provenance before comparing: manifest versions, Git commit/tree if available, and the active Rise baseline. Treat a downloaded `main` directory's version as a local label, not proof of a published or installable release. Read its installation policy without executing it.
2. Compare equivalent product boundaries. Distinguish a suite of registered plugins from one bar with internal shared components, and a standalone upstream reference from the user's Omarchy fork. Trace actual service ownership, persistence and host integration; both projects may already reuse the same shell process.
3. Build a capability matrix from concrete implementation and entry points, with docs used for intended contracts and explicit limitations. Trace dynamic provider records/registries before concluding a feature is absent from a literal-name search; generic adapters may support providers named only in the host contract. Distinguish discovered support from successful live account integration.
4. Separate portable CI declarations, local execution, native composed tests, screenshots and outstanding physical acceptance. Count files or physical source lines only as an explicitly scoped inventory, never as test passes, quality or performance. Do not claim CPU/RAM advantages without matched measurements.
5. Recommend bounded improvements that preserve approved features, visual hierarchy, layout and existing platform owners. Flag ownership conflicts and host-facade dependencies before suggesting cross-suite reuse; compatibility with a standard host does not prove plug-and-play support in a fixed internal widget registry. Preserve licensing notices when code is actually ported.
6. Turn approved recommendations into a short ordered implementation plan with one source owner and an independent tester. Split portable CI from native gates early, freeze milestone inputs, and assign one final broad-suite owner. Stop expanding the roadmap once only specific acceptance blockers remain.

## Supervised functionality, security and efficiency audits

1. Establish ownership before testing: have the implementing agent read the exact updated skill source and acknowledge its version. Assign one owner of production, workflows, existing tests and Git state in the shared checkout; let the independent tester prepare matrices, negative fixtures and patch artifacts in its own scratch before candidate freeze. Do not let the tester stash, change branches, commit or edit production to make a test pass. Freeze the review snapshot's code and tests while checks run, verify candidate hashes/modes before and after, and return reproductions to the implementation owner. If the implementer continues in the shared checkout, test only an independently verified immutable archive as described above; never mix that archive's identity with shared-tree wildcard discovery. When the user reserves delicate operations for Team Leader, limit the audit agent to read-only inspection and inert fixtures until the supervisor reviews its proposals.
2. Independently inventory source and installation: record HEAD, dirty paths, manifest version, tracked file bytes, symlink targets and executable bits, then snapshot scoped preferences and enabled plugins. Compare each dimension separately: content equality, executable-bit equality (`st_mode & 0o111`) and full permission mode (`stat.S_IMODE`). Count mode-only differences separately from content mismatches; files matching in bytes and execution bits must not become runtime-code differences merely because one copy permits group writes. Assess owner/group, writable ancestors and the actual trust boundary before labeling permissions a security finding; never apply blanket chmod to align copies. Classify runtime, metadata, documentation and test differences separately. An older installed manifest does not prove the running logic is old; local runtime patches can already match the newer source. Do not reinstall wholesale based on a version label.
3. Build a deduplicated JSON/CSV coverage matrix from the actual test inventory and runner: classify executable entrypoints, Qt/QML fixtures, helpers and test data, then map V1/V2, orientations, panel lifecycle, IPC, persistence, input, failure recovery and integrations to commands and evidence. A basename appearing in runner text is only a discovery hint; inspect indirect subrunners and fixture imports before assigning coverage. Record the entrypoint, coverage relationship, execution status, skip/block reason, command, exit code, log and candidate fingerprint; aggregate counts programmatically rather than calling every test-directory file an independent test. Run the broad suite, then applicable checks omitted by it. For each remaining driver, record a concrete disposition: executed with evidence, covered indirectly by a named entrypoint, helper/data rather than an entrypoint, obsolete against a verified current contract, requires external/manual effects, or still pending review. A generic 'not selected/safe boundary unknown' label is an open coverage gap, not audit completion. Classify the broad runner itself as executed when its command ran, and reconcile matrix totals against the actual entries. Keep a failed run, an isolated probe retry and a later full supervisor run as separate records; only the last full run establishes its own suite result. Mark unavailable checks and external-service boundaries explicitly rather than calling the runner exhaustive.
   - If execution approval expires, record that the tool did not run and retain the exact blocked command/environment. Do not replace it with equivalent executions or reuse an earlier green log as this audit's result. Request renewed explicit authorization for that operation; meanwhile continue only independently authorized static inventory/review, not execution disguised as analysis. After renewed authorization, retry through the normal approval path and stop again if it is denied.
4. Audit command construction, quoting, external inputs, helper permissions, update trust and secret handling without exposing credentials. Require a file/line, reachable path, reproduction and impact for each finding; distinguish confirmed vulnerabilities from hypotheses and lint warnings. For cache persistence, extract the exact production command array and exercise it only against a scratch-rooted path containing an apostrophe; this exposes shell-quoting failures that ordinary HOME paths conceal without touching real preferences. Preserve argv boundaries and newline/serialization semantics when proposing a fix. For updater confirmation probes, capture fake sudo/package-manager argv with inert scan/gate state and isolate notifications too; distinguish bypassing an optional prompt from bypassing sudo authentication or establishing remote execution. Simulate destructive, privileged, account, network and system-setting actions.
5. Measure efficiency over bounded intervals under recorded conditions. Use CPU-time deltas and memory/process samples; inspect timer overlap, subprocess churn, late callbacks and shutdown behavior before proposing optimizations. Attribute measurements to the integrated shell and its enabled plugins, not exclusively to Rise. Lifetime `ps` CPU is not an idle benchmark, and one RSS sample is not evidence of a leak. Do not disable plugins or change wallpapers merely to manufacture an improved baseline.
6. Return prioritized findings, missing coverage, minimal proposed changes and a failing regression for each reproducible defect. Have the supervisor inspect actual logs and diffs, apply approved sensitive operations with backups, then rerun affected checks and required final acceptance. Never present a sent task, reported total or green fixture as proof of completed live acceptance.

## Publish without conflating source and installation

1. Confirm the repository and requested publication scope before writing. Keep a skill repository, application checkout and installed plugin distinct; preserve an explicit stop or scope correction immediately.
2. Before an authorized merge/version bump, inspect the manifest, README, remote base and existing release workflow. Review the complete branch-to-base diff as well as the newest patch. Run final validation after the last covered edit and verify the PR is mergeable; report absent remote checks as absent, not green.
3. Push without force, verify the remote head, merge the reviewed head, then read back merged state and synchronize local main by fast-forward. If the existing workflow publishes the version, let it run rather than racing it with a duplicate manual release. Verify workflow success, remote manifest version, tag target and published release state.
4. Report installation separately: source publication does not update installed Git state or manifest. Reconcile installed changes and use the authorized deployment procedure if installation is included; otherwise state that boundary without claiming the whole installed tree was updated.

## Apply without overwriting local differences

Compare the checkout, Git base, and installation. The installation may contain old tests and legitimate differences even when the main code matches. Build minimal patches and run `git apply --check` in the installation directory, not in the already edited checkout. A context failure requires inspecting the difference; do not copy the entire file for convenience.

A local migration may leave removed paths in the index and new files still untracked. When discovering validation scripts, consider `git ls-files --cached --others --exclude-standard` and check that each file still exists. Do not interpret a difference in QML file counts as a regression without comparing files. Old empty adapters should only be removed after checking their consumers and preserving a copy when a backup is available.

If an installed test uses an old helper path, fix the fixture to use a temporary tree that preserves production relative paths. Do not run the real helper to compensate for a misplaced mock. Validate in the checkout and repeat relevant tests in the installation when those tests were actually updated.

Restart only after validating and applying authorized changes. Compare enabled plugins before/after, check `omarchy-shell shell ping`, and inspect the correct PID's log. After reload, poll the supported `quickshell-rise.variant` `current`, `state` and `error` methods together with `quickshell-rise.lifecycle` `ready` until a bounded stable condition is reached. Read the handler before interpreting a version label: a fallback expression can report V1 while no variant is running, so that label alone does not establish an unintended switch. Compare the saved active variant without overwriting it. Do not trigger another identical write, cache purge or restart merely because the first loading snapshot was not ready. Distinguish simulated tests, native loading, current session health, and remaining limitations in the report. None of these checks guarantees the absence of every future defect.

Before authorized native tests, record the variant and relevant preferences with contents and hashes; keep the snapshot outside the watched tree. Read the handler before clicking: left-clicking the clock toggles `clock12h`; it does not open a calendar. Restore changes made by the test and verify the original state while preserving concurrent user changes. For screenshots of rotated outputs, prefer selecting the output by name and check its transform before using global coordinates.

For reviews that apply changes to the installation, freeze and fingerprint the candidate's production and fixture files before final validation, then compare that fingerprint before deployment. HEAD alone does not identify a dirty candidate. Use modification times to discover possible stale evidence, not to prove byte identity. If any covered file changed after a green run, rerun affected checks and the required final acceptance suite; report which candidate each log actually covers. Record changed files, backups, checkout and installation results, and final session health. Distinguish simulated hotplug from physical disconnection, without changing real monitors merely to obtain evidence.
